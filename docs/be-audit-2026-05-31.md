## Section 6: Summary Scorecard

| Area | Score (0-10) | Top risk |
|---|---|---|
| N+1 queries | 4 | Analytics dashboard triggers N feedback queries per recording load |
| Pagination | 6 | GET /api/admin/users has no limit; analytics dashboard is unbounded per user |
| Indexes | 3 | recordings.user_id and feedbacks.recording_id have NO indexes; both are the hottest columns in the system |
| Connection pool | 7 | pool_recycle not set; single Uvicorn worker; within DO limits at MVP traffic |
| Security | 6 | Tier gate is a Phase-A stub returning "free" for all users; AI endpoints have no rate limits |

### Top 5 to fix before soft-beta (priority order)

1. **Add indexes on recordings.user_id and feedbacks.recording_id.** These are the two hottest columns in the system. Every analytics request is currently a full table scan compounded by N+1 full table scans on feedbacks.
2. **Add selectinload to all analytics and recording-history endpoints.** Eight endpoints access r.feedback in a Python loop with no eager loading. Fix with one import and one .options() call per endpoint.
3. **Rate-limit AI-calling endpoints per user.** POST /api/recordings/{id}/transcribe, POST /api/conversations/{id}/turns, and POST /api/writing/submit have no per-user rate limits. A single user can drain the Claude and AssemblyAI budgets in minutes.
4. **Wire P-105: _resolve_user_tier() returns "free" for all users today.** All tier gates on protected routes are currently no-ops. Any user who registers gets full access regardless of subscription status. Must be resolved before charging users.
5. **Paginate GET /api/admin/users.** No limit clause. Will become a full-table scan + 2N subqueries as user count grows.

### N+1 endpoint audit

**Classification key:** NONE = no N+1; LOW = potential but access is bounded or single-row; MEDIUM = loop over related objects, table is small today; HIGH = loop over related objects with no eager loading on unbounded dataset.

---

**GET /api/analytics/dashboard** -- RISK: HIGH N+1

Models: Recording, Feedback (via r.feedback relationship)
Eager loading: none
Query: `db.query(Recording).filter(user_id).order_by(...).all()` fetches all done recordings for the user. Then the handler accesses `latest_rec.feedback`, `r.feedback.note_globale` (scores list), and `r.feedback.goulet_nom` / patterns in a loop (analytics/coverage sub-call).
Pattern: 1 recording query + N feedback queries (one implicit SELECT per recording). For a user with 50 recordings this is 51 queries per page load.
Fix: `.options(selectinload(Recording.feedback))` on the recording query.

---

**GET /api/analytics/progress** -- RISK: HIGH N+1

Models: Recording, Feedback
Eager loading: none
Query: `.limit(last_n)` applied (1-100), but inside the loop `r.feedback.note_globale` triggers a lazy load per row.
N+1 count: up to 100 feedback queries per call.
Fix: selectinload.

---

**GET /api/analytics/pass** -- RISK: HIGH N+1

Models: Recording, Feedback
Eager loading: none
No limit. Accesses r.feedback.patterns_manquants, r.feedback.reflexes_detectes, r.feedback.goulet_nom in a loop over all done recordings for the user.
Fix: selectinload + consider adding a reasonable limit.

---

**GET /api/analytics/recurring** -- RISK: LOW

Models: Recording only. No relationship access in loop.
Query: .limit(last_n). The aggregate SQL query after is a direct subquery with func.count, not a loop.
Classification: NONE / LOW (single aggregate query pattern, not a lazy-load loop).

---

**GET /api/analytics/coverage** -- RISK: LOW

Models: Recording, TestTopic (separate queries, no relationship traversal in loop).
TestTopic is a bounded catalog. Recording list is per-user.
Classification: LOW (no relationship access in loop).

---

**GET /api/admin/dashboard** -- RISK: MEDIUM N+1

Models: Recording, User (joined), Feedback
Query: `.join(User).limit(20).all()`. Then accesses `r.feedback.overall_score` in the result loop.
N+1: 1 joined query + up to 20 feedback queries.
Admin-only endpoint; acceptable but should be fixed.
Fix: add joinedload or selectinload on Feedback.

---

**GET /api/admin/users** -- RISK: HIGH N+1 + compound subqueries

Models: User, Recording (via u.recordings), Feedback (via aggregate subquery)
Query: `db.query(User).order_by(...).all()` -- no limit.
Inside the loop for each user u:
- `len(u.recordings)` triggers a lazy load of the entire recordings relationship (1 SELECT per user).
- `db.query(func.avg(Feedback.overall_score)).join(Recording).filter(Recording.user_id == u.id).scalar()` runs a separate aggregate query per user.
Total queries: 1 user query + N recording queries + N avg queries = 2N+1.
At 100 users: 201 queries per admin page load. At 1000 users: 2001 queries.
Fix: use a single aggregate query with GROUP BY across all users instead of a per-user loop.

---

**GET /api/recordings** (lean list) -- RISK: NONE

Models: Recording, Feedback
Eager loading: `joinedload(Recording.feedback)` -- CORRECTLY IMPLEMENTED. Single LEFT OUTER JOIN. No N+1.
Pagination: .limit(limit) with le=100.
This is the only list endpoint in the codebase that uses eager loading.

---

**GET /api/recordings/history** -- RISK: HIGH N+1

Models: Recording, Feedback
Eager loading: none (different from GET /api/recordings which has joinedload).
Query: `.limit(50).all()` then `r.feedback.note_globale`, `r.feedback.score_le_fond`, etc. in loop.
N+1: up to 50 feedback queries per call.
Fix: add `.options(joinedload(Recording.feedback))` to match the pattern already in the same file.

---

**GET /api/writing/history** -- RISK: HIGH N+1 (explicit subquery in loop)

Models: WritingSubmission, WritingPrompt
Eager loading: none.
Query: `.limit(50).all()` on WritingSubmission. Then inside the loop: `db.query(WritingPrompt).filter(WritingPrompt.id == s.prompt_id).first()` -- this is an explicit N+1. Not lazy relationship access but the same problem pattern.
N+1: up to 50 explicit WritingPrompt queries per call.
Fix: add `.options(joinedload(WritingSubmission.prompt))` or fetch all prompt_ids and do a single IN query.

---

**GET /api/ecole/lessons** -- RISK: LOW

Models: EcoleLesson, UserEcoleProgress (two separate queries, merged in Python dict).
No relationship loop. EcoleLesson is a bounded catalog. Acceptable pattern.

---

**GET /api/modules** -- RISK: NONE

Models: RemediationModule only. No relationship traversal in list.

---

**GET /api/vocab/topics/{slug}/chunks** -- RISK: NONE

Models: VocabChunk only. No relationship traversal. Paginated.

## Section 4: Connection Pool and Deployment Audit

### SQLAlchemy engine (app/database.py)

```
pool_pre_ping: True
pool_size: NOT SET (SQLAlchemy default = 5)
max_overflow: NOT SET (SQLAlchemy default = 10)
pool_recycle: NOT SET
```

GOOD: pool_pre_ping=True catches stale connections after a Postgres restart without a manual reconnect.

RISK: pool_recycle not set. On long-lived single-worker deploys, connections held open for days can hit TCP-level timeouts on the DO managed Postgres side. pool_pre_ping catches most of these at checkout, but setting pool_recycle=1800 (30 minutes) is belt-and-suspenders practice and adds negligible overhead.

### Uvicorn / deployment (.do/app.yaml)

```
run command: alembic upgrade head && python -m uvicorn main:app --host 0.0.0.0 --port 8080
instance size: basic-xxs
instance count: 1
request_timeout_seconds: 180
worker count: 1 (Uvicorn default; no --workers flag, no gunicorn)
```

Single Uvicorn worker. FastAPI sync endpoints (def, not async def) run in a shared thread pool (default 40 threads). Under concurrent load:
- Each sync endpoint holds a DB connection for its duration
- Thread pool can reach 40 concurrent DB connections
- Pool allows only 15 (5 + 10 overflow)
- Under high concurrent load: up to 25 threads block waiting for a pool slot

At current MVP traffic (low concurrency) this is fine. Risk materializes at ~50+ concurrent users.

### DO Postgres tier

Plan tier from app.yaml: `production: false` (dev/hobby cluster, ~$7/month)

UNKNOWN: exact connection limit for this tier. DO Hobby Postgres typically allows 22-25 connections. Needs founder to verify via DO console (Settings > Connection Pooling or `SHOW max_connections;` in psql).

### Connection math

```
Max connections held simultaneously: 1 worker x (5 pool + 10 overflow) = 15 connections
DO Hobby Postgres limit: ~22-25 (UNKNOWN -- needs verification)
Result: within limits at current instance count
```

If instance count scales to 2: 30 connections, likely exceeds Hobby tier limit. The upgrade to DO Basic ($15/mo, typically 97 connections) should be the trigger when adding a second instance.

### pgbouncer

Not present. Acceptable at MVP. Should be evaluated when moving to multiple app instances or when connection exhaustion is observed in DO logs.

## Section 5: Security Checklist

**1. SQL injection**
PASS. All queries use SQLAlchemy ORM query builder. No `text()` raw SQL calls found in any router. No string interpolation into query strings.

**2. AuthN: JWT with refresh tokens**
PASS.
- Access tokens: HS256 JWT, 15-minute TTL, stateless verification.
- Refresh tokens: JWT with jti (UUID), 7-day TTL. Verification checks jti against Redis revoked-set AND DB row (not revoked, not rotated, not expired).
- Token rotation implemented: replaying a rotated refresh token invalidates the entire token chain.
- Email verification: random 32-byte token, SHA-256 hash stored in DB, 24-hour TTL. Required before first login.
- Password reset: same pattern, 1-hour TTL.
- Cookie flags: httponly=True, samesite=lax, secure=True in production only.
GOOD implementation. No obvious gaps.

**3. AuthZ: tier gating**
RISK -- CRITICAL pre-launch.
`_resolve_user_tier()` in `app/services/tiers.py` returns the string "free" for ALL users unconditionally (Phase A placeholder, awaiting P-105). Every `require_tier()` dependency and every `enforce_min_tier()` call therefore always sees the user as "free" tier regardless of what is stored in `users.subscription_tier`.

Effect: all authenticated endpoints labeled as requiring "subscription" or higher are currently bypassed. Any logged-in free user has full access to all premium endpoints. This is intentional (pre-payment soft launch) but must be wired before charging users. The DI shape is stable; the fix is a one-line change in `_resolve_user_tier` to return `getattr(user, "subscription_tier", "free")`.

**4. Rate limiting on AI-calling endpoints**
RISK.
Rate limiting exists in `app/services/rate_limit.py` and is applied to 5 auth endpoints (register, login, verify-email resend, password-reset request, password-reset confirm) using a dual-window Redis-backed limiter (5/15min, 10/1hr per IP).

NOT applied to:
- POST /api/recordings/{id}/transcribe (AssemblyAI call)
- POST /api/recordings/{id}/analyze (Claude call)
- POST /api/conversations/{id}/turns (Claude call per turn)
- POST /api/writing/submit (Claude call, async job)
- Any ElevenLabs TTS endpoints

A single authenticated user can trigger unlimited Claude, AssemblyAI, ElevenLabs API calls with no per-user or per-endpoint gate. This is a cost-runaway risk. The diagnostic_rate_limit.py service has per-user quota logic (quota check for diagnostics) but it is not consistently applied across all AI endpoints. Needs a unified per-user AI-call rate limiter applied as a FastAPI dependency on every AI-triggering POST.
